# 2026-11-09 Word Ladder II 코드 리뷰

## 오늘의 핵심
오늘은 Word Ladder II를 푸는 과정에서 내가 짠 코드의 구조를 다시 점검했다.

핵심은 이 문제의 어려움이,
"최단 경로를 찾는 것"과 "최단 경로를 모두 모으는 것"이 섞여 있다는 점이다.

그래서 단순히 BFS만 돌리거나,
한 번에 한 글자씩 바꾸는 로직만 구현하면 시간초과나 경로 누락이 생기기 쉽다.

## 1. 내가 짠 코드의 의도
네가 짠 코드의 핵심 아이디어는 대체로 좋다.

- `distance`를 이용해서 최단 거리 계산
- `mapping`을 이용해서 패턴 기반으로 다음 단어 찾기
- `map`에 최단 경로 연결 정보 저장
- 마지막에 DFS로 경로 복원

이 구조 자체는 정석 방향과 비슷하다.

하지만 구현에서 몇 가지가 문제였다.

## 2. 핵심 문제 포인트
### 1) `q.offer(next)`를 너무 많이 넣음
이 부분이 제일 큰 문제다.

```java
if(distance.get(word) + 1 == distance.get(next)) {
    if(next.equals(endWord)) found = true;
    map.computeIfAbsent(word, k -> new ArrayList<>()).add(next);
    q.offer(next);
}
```

이 코드는 다음 단어를 큐에 계속 넣고 있다.

그런데 중요한 건,
"최단 경로를 구성하는 간선인지"를 판별하지 않고,
혹은 같은 거리의 단어를 중복해서 큐에 계속 넣을 수 있다는 점이다.

결과적으로

- 큐가 불필요하게 커짐
- 중복 탐색이 계속 발생
- 시간초과로 이어짐

## 3. 왜 시간초과가 날 수 있는가
이 문제는 단어 수가 많아질수록,
모든 단어를 한 번씩 다시 체크하는 로직이 나빠진다.

네 코드에서 `getNextWord()`는 매번 단어를 변형해서 패턴을 만들고,
그 패턴을 `mapping`에서 꺼내는 방식이다.

그런데 `mapping`은 이미 만들어져 있지만,
`q`의 과정에서 중복 방문과 불필요한 재삽입이 계속 발생하면,
같은 단어들이 여러 번 처리된다.

즉,

- 같은 단어가 여러 번 큐에 들어감
- 같은 단어를 여러 번 계산함
- 결국 탐색 범위가 기하급수적으로 커진다.

이게 가장 큰 원인이다.

## 4. `distance`와 `map`의 역할 구분이 부족함
이 문제는 두 가지 역할이 나뉘어야 한다.

### `distance`
- 최단 거리 계산용
- BFS 레이어를 관리하는 역할

### `map` 또는 `graph`
- 최단 경로 그래프를 저장하는 역할
- 최단 거리 조건을 만족하는 간선만 추가

근데 네 코드에서는 아래처럼 섞여 있다.

```java
if(distance.get(word) + 1 == distance.get(next)) {
    map.computeIfAbsent(word, k -> new ArrayList<>()).add(next);
    q.offer(next);
}
```

이렇게 하면,

- `map`이 최단 경로 저장인지
- 큐에 넣는 목적이 무엇인지

가 애매해진다.

결과적으로 큐와 그래프가 서로 다른 역할을 하지만,
하나의 조건 안에서 동시에 처리되면서 제어가 복잡해진다.

## 5. 정석적인 접근법
이 문제에서 정석은 다음 단계로 나눈다.

### 1단계: BFS로 거리 계산
```java
Map<String, Integer> distance = new HashMap<>();
Queue<String> queue = new ArrayDeque<>();
queue.offer(beginWord);
distance.put(beginWord, 0);
```

이 단계에서는 각 단어의 최단 거리를 정확히 계산한다.

### 2단계: 패턴 기반으로 다음 단어 찾기
```java
Map<String, List<String>> patternMap = new HashMap<>();
```

예를 들어 `hit`는 `*it`, `h*t`, `hi*` 같은 패턴으로 변환해서,
같은 패턴을 가지는 단어들을 모은다.

이렇게 하면 너가 `getNextWord()`처럼 매번 전체 단어를 순회하는 비효율을 줄일 수 있다.

### 3단계: 최단 경로 그래프 구축
```java
if (distance.get(word) + 1 == distance.get(next)) {
    graph.computeIfAbsent(word, k -> new ArrayList<>()).add(next);
}
```

이 조건에 의해,
"최단 경로를 구성하는 간선만" 그래프에 남는다.

### 4단계: DFS로 경로 복원
```java
dfs(beginWord, endWord, path, result);
```

이때 DFS는 `graph`를 타고 들어가며,
최단 경로만 뽑아낸다.

## 6. 네 코드의 핵심 문제를 한 줄로 요약하면
네가 한 코드의 가장 큰 문제는,

"최단 경로 간선인지 판별하는 조건을 BFS와 경로 저장 로직에 동시에 섞어서 쓰고,
큐에 너무 자주 넣는 구조"라는 점이다.

즉,

- BFS는 최단 거리 계산용
- 그래프는 최단 경로 간선만 저장용
- DFS는 그 그래프를 따라 경로 추적

이 3개를 분리해서 생각해야 한다.

## 7. 왜 이게 중요하냐
이 문제는 하나의 BFS로 끝나지 않는다.

- 먼저 각 단어의 거리 계산
- 그 다음 최단 경로 간선만 남기기
- 그 다음 경로를 복원

이 세 단계가 모두 필요하다.

그래서 `distance`와 `graph`를 제대로 분리하지 않으면,
시간초과 또는 잘못된 경로가 발생한다.

## 8. 내가 보는 가장 큰 수정 포인트
네 코드에서 가장 먼저 고쳐야 하는 건,

```java
if(distance.get(word) + 1 == distance.get(next)) {
    q.offer(next);
}
```

이 부분이다.

이 `q.offer(next)`는 경로 복원을 위해서가 아니라,
최단 거리 계산을 위해서 필요한 건데,
그 로직을 경로 그래프와 함께 섞으면서 시간이 늘어난다.

정석 기준으로는,

- BFS는 `queue`에다가 최단 거리 계산용으로만 넣는다.
- `graph`는 최단 경로가 맞는 간선만 저장한다.
- DFS는 `graph`를 따라 경로를 뽑는다.

이렇게 분리해야 한다.

## 9. 오늘의 결론
네 코드의 방향은 틀리지 않았지만,

- BFS와 최단 경로 그래프의 역할 분리가 부족하고
- 중복 방문이 많아서 시간초과가 났다

는 점이 핵심이다.

이 문제에서 가장 중요한 건,

"BFS는 거리 계산용, DFS는 경로 복원용, graph는 최단 경로 간선만 남기는 구조"를 나누는 것

이다.

그래서 이걸 확실히 잡아야 시간 초과를 뚫을 수 있다.
